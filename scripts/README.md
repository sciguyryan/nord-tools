# Nord Tools acceptance VM manager

The Acceptance Manager provisions, tests and inspects a disposable Arch Linux guest from a CachyOS or Arch Linux host. Its Qt interface, CLI and `create-acceptance-vm.sh` compatibility entry point share the same Python backend. It does not change the host default route, firewall, DNS or VPN configuration.

Install host dependencies with `sudo pacman -S --needed pyside6 libvirt virt-install qemu-full passt curl xorriso openssh xterm`. Run `sudo -v` before using the CLI so privileged disk operations can use the existing credential. The GUI requests a sudo password for provision, rebuild and deletion operations.

Choose **Provision** to create a guest when none exists, or **Rebuild** to converge the acceptance environment. Rebuild reuses an existing guest only after positive checks of its libvirt definition, cloud-init readiness, provisioning attestation, required commands and unused acceptance baseline. Any mismatch or uncertainty triggers a clean replacement, which permanently destroys the disposable disk and guest data. The CLI supports `rebuild --plan` for read-only decision diagnostics and `rebuild --force` for an unconditional clean replacement. The GUI waits up to six minutes for SSH and a successful cloud-init status; CLI `provision` returns after VM creation, while CLI `rebuild` also waits for readiness and prints each stage as it runs. **Refresh** reports observed state without changing it, and **Wait for readiness** retries the checks without reprovisioning. **Console** opens virt-viewer for the guest display. **SSH terminal** connects through the loopback-only passt forward. **Delete VM** removes the named guest and generated disk and seed files, but preserves the image cache.

The guest uses passt userspace networking instead of a host bridge or libvirt NAT network. Passt supplies DHCP, DNS and outbound connectivity without adding host interfaces, routes, forwarding, NAT or firewall rules. SSH is forwarded only from `127.0.0.1:22222` by default; set `NORD_TOOLS_ACCEPTANCE_SSH_PORT` before provisioning to use another unprivileged port. The manager creates a dedicated, non-interactive Ed25519 key under `${XDG_CACHE_HOME:-$HOME/.cache}/nord-tools/acceptance/`, stores the private key with mode `0600`, and injects only its public key into the disposable guest. It does not depend on the user's personal key or SSH configuration. The NoCloud seed configures DHCP on the fixed VirtIO MAC, installs the test dependencies and enables sshd and the QEMU guest agent. Password authentication is disabled. A guest is ready only when cloud-init reports success over authenticated SSH and the guest Python standard library passes an independent health check. During rolling-release package upgrades, temporary Python/standard-library mismatches and failed cloud-init status invocations are retried within the overall six-minute readiness deadline. Only an explicit cloud-init error/degraded status, stopped guest or exhausted deadline fails readiness; failures include bounded package and cloud-init diagnostics. A failed cloud-init command alone does not establish failed provisioning.

Choose **Run acceptance tests** or run `python scripts/acceptance-manager.py test` after the guest is ready. The manager compares SHA-256 content hashes and executable modes of the working tree with the guest checkout, transfers only changed files, removes obsolete files and verifies the resulting manifest. Git metadata, dependency directories and caches are excluded. Source symlinks and unsupported file types are refused rather than copied implicitly. Node dependencies are reused only when the lockfile digest, Node/npm versions and `npm ls` dependency check agree; otherwise `npm ci` runs. The CLI streams each test stage and its output as it runs, colouring `PASS` green and `FAIL` red when the output is an interactive colour-capable terminal. Captured logs and non-interactive output remain plain text. It executes the full pytest suite, Ruff lint and format checks, Markdown lint, `tools/probe_network_isolation_adversarial_acceptance.py --run-privileged`, `tools/probe_application_lifecycle_acceptance.py --run-privileged` and the guest-only desktop and D1 host-domain probes. The host-domain stage runs last as a detached systemd service because its deny barrier is expected to interrupt SSH. Success requires remote access to return after verified retirement and a complete durable D1 result. A timeout leaves the barrier and evidence intact for console inspection; rebuild the disposable guest rather than weakening uncertain protection. These privileged stages cover production provisioning, real WireGuard exchange and tunnel loss, dual-stack firewall and route policy, DNS and resolver confinement, registered direct and VPN-bound packet behaviour, a nested Wayland/X11/D-Bus desktop session, interrupted recovery, and cooperating-process SIGKILL/lock handover. The test action checks the guest's complete provisioned package contract before uploading the tree; a stale guest must be rebuilt through the manager. D1 has passed on the documented static-egress guest; the evidence does not claim compositor-specific desktop services, real-reboot acceptance or the D2-D4 host-domain requirements described in the repository TODO.

The official Arch Linux cloud QCOW2 image is cached in `${XDG_CACHE_HOME:-$HOME/.cache}/nord-tools/acceptance/images/`. The script downloads the current published SHA-256 digest and verifies the cached bytes before reuse, downloading the image again only when absent or invalid. The cached source image is never resized. A checksum served from the same mirror provides integrity checking but not independent publisher authentication. The cache survives guest deletion.

The CLI supports `status`, `address`, `ready`, `wait`, `provision`, `rebuild`, `start`, `stop`, `console`, `ssh`, `test`, `cache` and `remove`. CLI `rebuild` may be destructive and is intended for deliberate, scripted use; the GUI requests confirmation. The first rebuild after introducing provisioning attestation recreates legacy guests, which cannot establish the new contract. A guest that has run privileged acceptance is not considered a certified clean baseline and will be rebuilt on a subsequent `rebuild`; `test` can still reuse a ready guest, with the existing probes responsible for their own isolation and cleanup. Clean release acceptance must use `rebuild --force`. The script requires a working system libvirt connection and permission to manage it. `address` reports only an IPv4 address associated with the configured guest MAC; SSH itself always uses the loopback passt endpoint.

All privileged acceptance commands run inside the disposable guest. A failed probe stops the matrix and retains its guest-side evidence for inspection. The host remains outside the tested network topology and is not used as the privileged acceptance target.

## Failure evidence export

When a privileged production WireGuard probe fails and reports a retained `/tmp/nt-production-wg-*` directory, `test` attempts to export a restricted, redacted set of JSON evidence files to a private `/tmp/nord-tools-acceptance-*` directory on the parent. The guest remains available and the original failure is never replaced by an export failure. Private keys and other non-JSON files are excluded. Treat exported diagnostics as potentially sensitive despite redaction and review them before sharing.

Run `python scripts/acceptance-manager.py evidence` while the guest is running to retrieve the latest retained production WireGuard evidence independently. This command does not rebuild or reset the guest. The exported manifest lists omitted files; the original guest evidence remains in place for further inspection.
