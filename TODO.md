# Nord Tools outstanding work

This is the canonical forward-looking work list. It contains requirements that are unfinished, incompletely verified or still require an explicit release decision. Completed implementation history belongs in Git, the changelog and the existing design and acceptance documents. A checked item was removed only when the source tree and available acceptance evidence supported its completion within the stated scope; an unproven remainder is retained below. Do not infer production security guarantees from offline or separate disposable component tests.

## Release authority boundary

The release target is the **cooperating-process authority model** described in `docs/PRIVILEGED-AUTHORITY-BOUNDARY.md`. Nord Tools executors share a protected lifecycle lock and verify ownership before privileged mutation. Independent privileged kernel/network/mount mutators, or actors deliberately bypassing that lock with equivalent authority, are outside the supported safety guarantee. Preserve fail-closed behaviour on uncertain evidence, document deployment isolation requirements and do not describe this boundary as atomic kernel-enforced ownership. Expanding the threat model requires a separate explicit decision, not an implicit release blocker.

## Current acceptance baseline and limits

The 9 November 2026 disposable Arch Linux guest run completed 1,273 pytest tests and 357 subtests, Ruff lint and formatting, Markdown lint and the privileged lifecycle, application, real WireGuard, dual-stack, DNS, desktop and platform-contract probe suites. The production-owned dual-stack profile stage passed within both privileged matrices, including B2 application bypass and B3 failure, recovery, readback and restart checks. The application matrix passed C1 through C3, including the production registered launch gate and concurrent lifecycle and packet behaviour. The separate guest desktop stage passed C4 with a nested Wayland/X11/D-Bus session. B4 records the exact accepted Arch kernel and network-tool profile; other versions remain unaccepted until they pass the same capability and privileged matrices. The acceptance manager in `scripts/acceptance-manager.py` provisions the guest with passt userspace networking. This is evidence for the executed probe scopes, **not** for host-domain default protection, compositor-specific desktop services or every deployment environment. The source-linked QA inventory is maintained in [`docs/RELEASE-ACCEPTANCE-MATRIX.md`](docs/RELEASE-ACCEPTANCE-MATRIX.md); it must be updated as new evidence is accepted.

## Phase B: Integrated production VPN confinement

- [x] **B1: Exercise one production-installed, ownership-verified real WireGuard profile with its production nftables rules, IPv4/IPv6 routes and pinned namespace resolver active together.** The dual-stack production confinement probe verified both live address families, the pinned endpoint exception, resolver and route readback, ownership-aware retirement and unchanged host networking in the disposable guest.
- [x] **B2: Verify IPv4/IPv6 DNS packet confinement and application-level bypass resistance on that installed profile.** The production-owned namespace probe passed real DNS request/response exchanges over both WireGuard families, underlay UDP/TCP and alternative DNS refusal with a reachable dual-stack underlay, and tunnel-down fail-closed behaviour in the disposable guest.
- [x] **B3: Prove fail-closed behaviour under failed establishment, tunnel shutdown/restart, malformed or uncertain firewall/resolver observations and interrupted provisioning.** The production profile passed late-establishment rollback and explicit recovery, unavailable-peer and established-tunnel loss/restart, malformed firewall and unsafe resolver readback refusal, ownership-aware retirement and exact host-state comparison. The enclosing matrix also passed SIGKILL recovery after underlay, WireGuard and routing checkpoints.
- [x] **B4: Validate supported kernel and tooling combinations for production nftables readback, routing and resolver inspection.** The accepted Arch profile is Linux `7.2.x-arch1`, iproute2 `7.3.0`, nftables `1.1.7` and wireguard-tools `1.0.20260223`. Startup restoration now checks those versions, live JSON and field-readback shapes, and trusted namespace resolver storage before creating stores or mutating networking. Other combinations remain refused until separately accepted.

## Phase C: Registered application lifecycle and desktop behaviour

- [x] **C1: Accept the actual production registered VPN-bound launch gate.** The regular privileged application matrix now invokes the public launch command against production-provisioned generations A and B. It verifies the executed child's namespace and non-root identity, exact generation and allocation lease, refusal before provisioning without execution or a residual lease, and process-exit-verified lease release. Packet and desktop behaviour are separately scoped to C3 and C4.
- [x] **C2: Exercise concurrent launched applications.** The privileged application matrix now keeps two shared, two isolated and one explicit direct registered child alive together. It verifies shared allocation reuse, distinct isolated namespaces, exact lease membership, lease-protected retirement, verified cleanup and refusal without execution or direct fallback after a VPN allocation is retired. Packet behaviour is accepted separately under C3.
- [x] **C3: Run IPv4/IPv6 and application DNS/leak acceptance with real direct and VPN-bound processes running concurrently, including tunnel loss.** The privileged application matrix now keeps lease-gated VPN-bound and explicit direct registered children alive together through dual-stack DNS, UDP/TCP underlay DNS refusal, peer loss and tunnel recovery. The direct child retains working host-loopback traffic while the same VPN child remains fail closed, then recovers without relaunch. Historical retired generations are excluded when selecting and leasing the active allocation.
- [x] **C4: Validate common Linux desktop launch environments and integration boundaries.** Explicit desktop mode now forwards only validated local Wayland, X11, Xauthority and user D-Bus state. The disposable guest passed real protocol requests from registered direct and VPN-gate children and their descendants after non-root identity transition. The accepted stack is headless Weston `15.0.1`, Xvfb `21.1.25` and D-Bus `1.16.2`; compositor portals, notifications, GPU rendering and desktop-specific activation remain outside this evidence.

## Phase D: Host-domain default protection

- [ ] **D1: Accept the implemented host-domain protection lifecycle in a disposable guest with a supported static-egress configuration and no recognised competing manager.** Verify deny-first firewall activation, endpoint-specific underlay allowance, dual-stack policy routing and resolver state against live packet evidence.
- [ ] **D2: Prove failure and recovery guarantees.** Cover real tunnel loss, failed activation, interruption/process death, firewall and DNS readback uncertainty, barrier-last deactivation and preservation of host integrity.
- [ ] **D3: Exercise actual guest reboot and split early-barrier/network-online systemd restoration.** Check protected startup ordering, convergence and explicit recovery after interrupted transitions.
- [ ] **D4: Decide and document host-side deployment compatibility.** Do not silently claim support for hosts with competing VPN, firewall or network managers beyond the accepted static-egress boundary; test additional configurations only if support is explicitly selected.

## Phase E: Provider operations and live management

- [ ] **E1: Complete secure provider credential acquisition, validation and rotation, with no secrets in plans, logs, subprocess arguments or test artefacts.** Integrate provider endpoint/server selection, including fastest/country preferences where supported, and define deterministic failure behaviour at boot.
- [ ] **E2: Verify complete operational default, shared and isolated profile workflows with real provider configurations.** Distinguish the accepted named-profile and generation ownership foundations from unverified provider selection and live service behaviour.
- [ ] **E3: Define and implement general in-place live updates, if supported, using fresh owned-state inspection and evidence-gated apply/update semantics.** Existing create-only apply, generation-based replacement and verified removal are accepted; do not rebuild them or imply that disputed-resource drift is safe to repair automatically.
- [ ] **E4: Specify disputed-resource drift handling and operator recovery.** Preserve quarantine and refusal for uncertain ownership; implement repair only where independently verifiable evidence makes mutation safe within the cooperating-process model.
- [ ] **E5: Complete dependency, platform and privilege preflight for the supported operational configurations.** Keep unsupported environments explicit and non-mutating by default.

- [ ] **F5: Produce a release-readiness assessment** identifying any unresolved security, operational or verification blockers, and verify release packaging excludes Git metadata and generated caches.

## Delivery rules

Complete one bounded increment at a time. Each change must preserve existing accepted behaviour, include appropriate regression coverage and a conventional-tagged Git commit message, and distinguish successful local/static checks from privileged guest results. Never mark a requirement complete merely because an earlier checkbox was ticked; require matching implementation and evidence, or retain the outstanding portion here.
