# Nord Tools acceptance VM manager

The Acceptance Manager provisions, tests and inspects a disposable Arch Linux guest from a CachyOS or Arch Linux host. Its Qt interface, CLI and `create-acceptance-vm.sh` compatibility entry point share the same Python backend. It does not change the host default route, firewall, DNS or VPN configuration.

Install host dependencies with `sudo pacman -S --needed pyside6 libvirt virt-install qemu-full passt curl xorriso openssh xterm`. Run `sudo -v` before using the CLI so privileged disk operations can use the existing credential. The GUI requests a sudo password for provision, rebuild and deletion operations.

Choose **Provision** to create a guest when none exists, or **Rebuild** to converge the acceptance environment. Rebuild reuses an existing guest only after positive checks of its libvirt definition, cloud-init readiness, provisioning attestation, required commands and unused acceptance baseline. Any mismatch or uncertainty triggers a clean replacement, which permanently destroys the disposable disk and guest data. The CLI supports `rebuild --plan` for read-only decision diagnostics and `rebuild --force` for an unconditional clean replacement. The GUI waits up to six minutes for SSH and a successful cloud-init status; CLI `provision` returns after VM creation, while CLI `rebuild` also waits for readiness and prints each stage as it runs. **Refresh** reports observed state without changing it, and **Wait for readiness** retries the checks without reprovisioning. **Console** opens virt-viewer for the guest display. **SSH terminal** connects through the loopback-only passt forward. **Delete VM** removes the named guest and generated disk and seed files, but preserves the image cache.

The guest uses passt userspace networking instead of a host bridge or libvirt NAT network. Passt supplies DHCP, DNS and outbound connectivity without adding host interfaces, routes, forwarding, NAT or firewall rules. SSH is forwarded only from `127.0.0.1:22222` by default; set `NORD_TOOLS_ACCEPTANCE_SSH_PORT` before provisioning to use another unprivileged port. The manager creates a dedicated, non-interactive Ed25519 key under `${XDG_CACHE_HOME:-$HOME/.cache}/nord-tools/acceptance/`, stores the private key with mode `0600`, and injects only its public key into the disposable guest. It does not depend on the user's personal key or SSH configuration. The NoCloud seed configures DHCP on the fixed VirtIO MAC, installs the test dependencies and enables sshd and the QEMU guest agent. Password authentication is disabled. A guest is ready only when cloud-init reports success over authenticated SSH and the guest Python standard library passes an independent health check. During rolling-release package upgrades, temporary Python/standard-library mismatches and failed cloud-init status invocations are retried within the overall six-minute readiness deadline. Only an explicit cloud-init error/degraded status, stopped guest or exhausted deadline fails readiness; failures include bounded package and cloud-init diagnostics. A failed cloud-init command alone does not establish failed provisioning.

Choose **Run acceptance tests** or run `python scripts/acceptance-manager.py test` after the guest is ready. Development mode is the default. It fingerprints each pytest file with its transitive local Python imports, shared pytest configuration and guest tool identity. Ruff, Markdown lint and the network, application, desktop, D1, D2 and D3 scenarios have separate fingerprints. A unit executes when its implementation, tests, fixtures, configuration or relevant environment has changed; an equivalent prior development pass is reported as reused rather than as fresh execution. Missing, unsafe or malformed cache data causes execution, never a cached pass. Changes to shared pytest configuration invalidate every pytest file, while unresolved Python dependency analysis broadens execution conservatively. The private, workspace-bound result cache is stored under `${XDG_CACHE_HOME:-$HOME/.cache}/nord-tools/acceptance/` and survives guest rebuilding.

The source deployment contract remains independent of result reuse. Before selection, the manager compares SHA-256 content hashes and executable modes of the working tree with the guest checkout, transfers changed files, removes obsolete files and verifies the complete resulting manifest. Git metadata, dependency directories and caches are excluded. Source symlinks and unsupported file types are refused. Node dependencies are reused only when the lockfile digest, Node/npm versions and `npm ls` dependency check agree; otherwise `npm ci` runs. The CLI streams executed stages, colouring `PASS` green and `FAIL` red in an interactive colour-capable terminal. Pass `--colourblind` or `--colorblind` to use blue and orange instead. Text labels remain present, while captured logs and non-interactive output contain no colour sequences.

Use `--explain-selection` to print each execution or reuse decision. `--scenario` accepts `quality`, `network`, `application`, `desktop`, `d1`, `d2`, `d3` or `all`, and may be repeated for a targeted development run. `--invalidate UNIT` forces one selected unit to execute. `--force-complete-run` executes the complete selected scope and refreshes its development results; `--no-result-cache` neither reads nor writes reusable results. A privileged scenario that must execute requires a clean disposable guest. Unchanged privileged scenarios may reuse their host-side development evidence without mutating an already-used guest.

```bash
python scripts/acceptance-manager.py test --explain-selection
python scripts/acceptance-manager.py test --scenario quality
python scripts/acceptance-manager.py test --scenario d3
python scripts/acceptance-manager.py test --scenario quality --force-complete-run
python scripts/acceptance-manager.py test --scenario quality --invalidate pytest:tests/test_host_protection.py
```

Final mode rejects partial scenario selection, ignores every reusable development result and executes the complete quality and privileged matrix. It also refuses a guest that has already run privileged acceptance. Successfully executed final units seed the development cache for later equivalent runs; they are still reported as reused development evidence rather than new execution when consumed later. Provision a clean guest deliberately before requesting final evidence:

```bash
python scripts/acceptance-manager.py rebuild --force
python scripts/acceptance-manager.py test --mode final
```

The host-domain stages remain serial because each deny barrier can interrupt SSH. D1 and D2 run as separately evidenced detached services; D3 uses the QEMU guest agent across a genuine reboot and requires normal SSH to return after verified retirement. A timeout retains the barrier and evidence for console inspection, so rebuild the disposable guest rather than weakening uncertain protection. The scenarios cover production provisioning, real WireGuard exchange and tunnel loss, dual-stack firewall and route policy, DNS and resolver confinement, registered direct and VPN-bound packet behaviour, a nested Wayland/X11/D-Bus desktop session, interrupted recovery, and cooperating-process SIGKILL and lock handover. Result reuse is diagnostic development evidence only. It does not extend the acceptance boundary recorded in the repository TODO and release acceptance matrix.

The official Arch Linux cloud QCOW2 image is cached in `${XDG_CACHE_HOME:-$HOME/.cache}/nord-tools/acceptance/images/`. The script downloads the current published SHA-256 digest and verifies the cached bytes before reuse, downloading the image again only when absent or invalid. The cached source image is never resized. A checksum served from the same mirror provides integrity checking but not independent publisher authentication. The cache survives guest deletion.

The CLI supports `status`, `address`, `ready`, `wait`, `provision`, `rebuild`, `start`, `stop`, `console`, `ssh`, `test`, `cache` and `remove`. CLI `rebuild` may be destructive and is intended for deliberate, scripted use; the GUI requests confirmation. The first rebuild after introducing provisioning attestation recreates legacy guests, which cannot establish the new contract. A guest that has run privileged acceptance is not considered a certified clean baseline and will be rebuilt on a subsequent `rebuild`. Development tests may still use that ready guest when every required privileged scenario is reusable. Clean final acceptance requires `rebuild --force` followed by `test --mode final`. The script requires a working system libvirt connection and permission to manage it. `address` reports only an IPv4 address associated with the configured guest MAC; SSH itself always uses the loopback passt endpoint.

All privileged acceptance commands run inside the disposable guest. A failed probe stops the matrix and retains its guest-side evidence for inspection. The host remains outside the tested network topology and is not used as the privileged acceptance target.

## Failure evidence export

When a privileged production WireGuard probe fails and reports a retained `/tmp/nt-production-wg-*` directory, `test` attempts to export a restricted, redacted set of JSON evidence files to a private `/tmp/nord-tools-acceptance-*` directory on the parent. The guest remains available and the original failure is never replaced by an export failure. Private keys and other non-JSON files are excluded. Treat exported diagnostics as potentially sensitive despite redaction and review them before sharing.

Run `python scripts/acceptance-manager.py evidence` while the guest is running to retrieve the latest retained production WireGuard evidence independently. This command does not rebuild or reset the guest. The exported manifest lists omitted files; the original guest evidence remains in place for further inspection.

### Dependency-aware test impact policy

The development reuse manager reads the version-controlled `tests/impact-rules.json` policy. Each rule has a unique `id`, `when_changed` repository-relative glob patterns, `invalidate` unit-ID glob patterns and an explanatory `reason`. Rules add dependencies to the automatic Python import closure; they cannot remove detected dependencies or bypass `--force-complete-run`. The policy file itself is fingerprinted for every selected unit, so changing a rule invalidates existing cached passes. A missing, malformed or symlinked policy fails closed before execution planning. `--explain-selection` lists matching impact rules and reasons alongside execution decisions. Review rules whenever adding dynamic imports, subprocess-invoked tools or cross-cutting configuration.

Non-Python inputs that static analysis cannot associate with a specific Python file conservatively invalidate all pytest units. Dynamic imports with non-literal module names expand to the complete local Python source set, and subprocess execution conservatively includes local executable and configuration inputs. These choices intentionally favour correct execution over maximum cache reuse. Privileged scenarios always run when selected because a source fingerprint alone cannot certify the guest's mutable network, boot or fixture state. The private result cache remains useful for deterministic quality checks, but previous privileged passes never substitute for fresh live acceptance. Final mode and `--force-complete-run` continue to execute the complete selected matrix.
