# Nord Tools development plan

This document tracks the agreed sequence of work. It distinguishes completed foundations from work that has not yet been implemented or accepted. Update the status and acceptance notes as each increment is delivered. Do not mark live networking features complete on the strength of offline tests alone.

### Part 7: Startup persistence and safe cleanup

- [x] Increment 7.1: durable creation-time ownership records, privileged verification and interrupted-creation recovery preflight, with batch-level rejection of foreign or uncertain resources. Offline tests and the privileged acceptance probe (`sudo python tools/probe_ownership_preflight.py --run-privileged`) passed on the user's Arch Linux test system. Boot-session continuity is a documented limit, not an unforgeable certificate.
- [x] Increment 7.2: read-only persistent desired-state reconciliation. Actual per-profile state is derived from verified ownership evidence, configuration drift is only detectable through recorded provisioned configuration, and every non-converged outcome is a plan — never an execution. Transient intent is structurally excluded.
- [x] Increment 7.3: systemd restoration of persistent desired state. `manage startup-plan` and `startup-install` render and install `nord-tools-restore.service` with `network-online.target` ordering and persistent-only path conditions; `manage restore-startup` runs an authorised, journal-gated boot executor which reconciles against a fresh ownership preflight, provisions only pinned profiles whose owned resources are absent in the current boot session, retires journal records for resources a reboot lost, records owner bindings at creation time and appends a bounded startup run record per boot. Transient intent is rejected outright. A failed attempt rolls back only its own namespace, records failed lifecycle evidence and leaves its intent uncertain. The restoration probe (`sudo python tools/probe_restore_startup.py --run-privileged`) passed creation-time binding and repeat-convergence checks on the user's Arch Linux test system after corrective iterations; the default profile's host-domain routing, provider server selection at boot, and real-tunnel DNS/IPv6 conformance remain open and are reported rather than restored.
- [x] Increment 7.4: ownership-aware cleanup and reset. `manage cleanup` plans and, on explicit confirmation, executes verified-resource removal with dry-run default, `--intents` required for execution, whole-profile refusal on any disputed ownership evidence, preserved desired profiles and unclaimed foreign observations, dependents-before-prerequisites deletion ordering, recorded owner identity re-verified at the moment of each deletion, observed-absence confirmation before retirement, and nothing ever flushed on the host outside owned namespaces and interfaces. `manage clear-ownership` performs the confirmed full reset and byte-verified archives of the four ownership stores before re-creating them empty. The corrected cleanup probe passed during the user's privileged Part 8.1.6 acceptance sequence; the separate verified `clear-ownership --execute` retirement also confirmed absence and consistent retirement of four retained test allocations. Interrupted-cleanup resume belongs to Part 7.5.
- [x] Increment 7.5: crash, restart and interrupted-cleanup recovery. `manage recovery` plans and, on operator confirmation, resolves the interrupted evidence left by process death: the boot wall inside every `restore-startup` completes certified bookkeeping, rolls back a half-built creation recorded with a pending intent and resolves records for absent resources, while the operator's execution adds resume of confirmed retirements and evidence-gated resolution of uncertain intents. Lookalikes, unbound live resources and mixed evidence are reviewed, never touched, and profiles are classified whole around lookalikes so no executable item shares evidence with a lookalike. Recovery is idempotent and host-isolated in the same way as every other executor. Privileged acceptance with real process death is provided via `sudo python tools/probe_recovery.py --run-privileged`, which stops a restore child at a deterministic test-only checkpoint after durable creation intent but before the namespace kernel callback, terminates it, reconciles the pending intent and staged dependent allocations, and finishes with confirmed cleanup. The later `--after-binding` checkpoint additionally exercises interruption after creation of an identity-bound namespace; neither checkpoint covers interruption after every subsequent interface and routing operation.
- [x] Increment 7.6: integrated persistence and cleanup acceptance. `tools/probe_startup_restoration_lifecycle.py --run-privileged` runs the whole workflow as one matrix: two pinned profiles restore while a different transient policy is configured and proven inert; the secondary profile is retired and its recreation is interrupted at a deterministic durable-intent checkpoint before kernel mutation; recovery converges both profiles; removing an application reference is pure bookkeeping; authorised cleanup retires exactly the departed profile while the shared generation survives; repeat runs converge without kernel changes; final verified teardown retires the surviving fixture; and host IPv4/IPv6 routes, nftables rules and resolver contents are compared across every stage boundary. Recovery scopes a recreated profile to its current non-retired generation. Host comparison exempts only identity-bound fixture routes and changing nftables counter readings.
- [x] Complete privileged acceptance of the integrated Part 7 matrix against the final corrected source. The standalone matrix and the fresh matrix inside Part 8.1.6 passed on the user's Arch Linux test system on 3 November 2026.

## Outstanding production ownership and recovery boundary

Part 2's offline lifecycle foundations and the Part 7 executors have automated coverage. Ownership preflight, restoration, confirmed cleanup, deterministic pending-intent recovery, the integrated Part 7 matrix and the five-stage Part 8.1.6 runner have passed on the user's Arch Linux test system. They do not satisfy adversarial race-safe ownership: bind continuity holds within one boot session, and a hostile process with store-directory access stays outside the evidence model. Before claiming production authority, require privileged adversarial tests and the live update and replacement authorities. Resource names, journal claims, inode fingerprints and completed intents remain insufficient deletion authority on their own.

- [ ] Bind durable intents and independent creation-time ownership evidence into an authorised privileged WireGuard executor with a transactional, crash-recoverable state model. The 7.1 owner-record preflight supplies the binding record and verification layer, Part 7.3's boot restoration executor consumes both for transactional provisioning of absent resources, Part 7.4 adds the confirmed verified cleanup, and Part 7.5 resolves interrupted evidence conservatively; the remaining executor authority (live update and replacement cut-over over verified resources) remains outstanding.
- [x] Connect the journal-gated creation adapter (durable intent before the privileged callback, verified completion afterwards) to the executors without granting mutation authority to offline plans: the 7.3 restoration path runs through it, and the 7.4 cleanup path applies the same gate to every retirement.
- [x] Integrate optional pinned namespace DNS resolver installation into the authorised provisioning lifecycle, with destination route, peer AllowedIPs and resolver-content verification. Cleanup of namespace resolver files remains an explicit ownership-verified operation; deployments without pinned DNS retain their existing behaviour.
- [ ] Prove production-installed firewall and resolver DNS packet confinement on the same real WireGuard tunnel, including IPv4/IPv6, application DNS bypass attempts, tunnel loss and failed establishment. Disposable dual-stack DNS-shaped UDP exchange and tunnel-loss checks have passed, but do not discharge this requirement.
- [ ] Verify real WireGuard endpoint exceptions and production failure-injection recovery together with the installed production firewall and resolver before claiming integrated fail-closed behaviour. Separate endpoint, recovery and host-isolation probes have passed.

Final lifecycle acceptance note: the probes use validated host inventories rather than locale-dependent missing-device messages, compare nftables configuration while ignoring only live packet and byte readings, and scope namespace absence to the current fixture. The integrated recovery stage retires the secondary profile before interrupting its recreation at the durable-intent checkpoint. Historical retired allocations no longer contaminate the recreated generation, and successful Part 7 runs perform verified final teardown before removing their temporary ownership stores. These corrections passed standalone Part 7 and the complete Part 8.1.6 matrix on 3 November 2026.

Accepted disposable packet acceptance: a combined opt-in privileged runner now exercises the existing disposable dual-stack endpoint-exception and simulated-tunnel route-loss probes. This is evidence for the underlying kernel policy and route behaviour, not proof of production WireGuard or DNS leak confinement. Production-installed real-tunnel packet confinement remains outstanding.

Production route hardening: the provisioning route installer now pins both IPv4 and IPv6 namespace default routes to WireGuard, regardless of the tunnel address family. Failure to install either route aborts provisioning. This does not certify usable dual-stack service, real-tunnel packet confinement or DNS protection; those remain open acceptance requirements.

Production routing readback: the authorised restoration path verifies both default routes and the endpoint route against live namespace state before activation. The standalone real WireGuard and simulated-tunnel acceptance probes passed, but production-installed firewall and real WireGuard packet confinement on the same tunnel remains unverified.

Accepted integrated routing acceptance: `tools/probe_production_routing_acceptance.py` now runs production provisioning integration, real WireGuard exchange/loss with host-integrity checks, and the disposable dual-stack firewall/routing probes together. These are separate evidence scopes; a production-installed firewall with real-tunnel packet and restart verification remains outstanding and must not be inferred from the combined pass.

Accepted DNS confinement component: the authorised restoration path now checks DNS destination routes, live WireGuard peer AllowedIPs and exact namespace resolver contents before activation. A disposable privileged probe exercises dual-stack DNS-shaped UDP delivery through a real WireGuard pair, resolver visibility, tunnel loss and host integrity. Production-installed firewall packet-level DNS confinement and application DNS bypass remain separate outstanding acceptance requirements.
