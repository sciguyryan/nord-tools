# Production provisioning contract

The read-only `validate_provisioning_contract` boundary correlates the configured VPN profiles with validated public WireGuard specifications and candidate namespace/interface allocations. Every configured profile must have exactly one tunnel specification and exactly one candidate namespace and interface. Additional profiles, missing resources, reused allocation tokens and mismatched identifiers are refused.

The result is deliberately credential-free and reports `ownership_verified: false`, `mutation_authorised: false` and `network_changes_applied: false`. An allocation token does not prove that Nord Tools created or still owns a kernel resource. The contract cannot replace creation-time owner bindings, fresh kernel observations, lifecycle locking, durable operation intents or mutation-time ownership verification. Those requirements remain the privileged executor's responsibility.

This boundary establishes a shared shape for subsequent production provisioning integration. It is not a new privileged entry point, and it does not change existing experimental provisioning or operational management behaviour.

The read-only `validate_provisioning_owner_bindings` check additionally requires the complete set of recorded creation-time owner bindings to match the allocation ledger by token, resource kind and identifier. Missing, additional, malformed or conflicting records are refused. A consistent recorded binding is historical evidence only: the result continues to report unverified ownership and no mutation authority. Production execution still requires fresh kernel identity checks, an authorised lifecycle lock and a durable operation intent at the actual mutation boundary.

## Production creation boundary

The boot restoration executor validates its actual four-resource creation batch before appending new allocations to the lifecycle journal. The batch consists of the namespace, WireGuard interface, namespace-side underlay and host-side underlay. Profile, kind, name and allocation-token collisions with existing journal entries are refused. A fresh kernel observation also refuses newly occupied candidate names before recording the creation intent. The executor then retains its existing lifecycle lock, durable intent, descriptor-bound namespace creation, progressive creation-time owner binding and verification sequence.

The offline two-resource contract remains a diagnostic contract for the tunnel and namespace pair. It does not require creation-time owner bindings for resources that have not yet been created. Neither the offline contract nor the four-resource validation is independent authority to mutate kernel state. Independent privileged actors can still race the observation and creation boundary; the documented cooperative authority model and conservative failure behaviour remain in force.

## WireGuard interface creation identity

The disposable WireGuard creation path checks the namespace-local interface index immediately after creating the device and again after applying peer configuration. A missing, invalid or changed index stops subsequent address assignment and activation. This is a creation-time consistency check, not an ownership claim about an arbitrary pre-existing interface. The caller remains responsible for durable intent, descriptor-bound namespace ownership and rollback. Independent privileged mutation between checks remains outside the cooperating-process authority model.

## WireGuard peer configuration

The disposable configuration path accepts one or two canonical tunnel addresses with distinct address families, plus an optional persistent keepalive interval from 0 to 65535 seconds. At least one tunnel address must match the endpoint family. Zero leaves the peer setting unset; a positive interval is passed explicitly to `wg set` alongside the validated endpoint and allowed IP networks. Malformed addresses, duplicate families, booleans, strings and out-of-range intervals are refused before kernel mutation. The public plan records the addresses and interval but never carries the private key.

The private key is still supplied through an inherited descriptor, not an argument or a persistent configuration file. The subsequent restoration readback verifies live peer configuration; this configuration step alone does not provide persistent production credentials or establish fail-closed routing. Those require later integration and privileged acceptance.

## WireGuard live peer verification

The production restoration executor checks the derived local public key and the sole expected peer, then reads back the peer endpoint, allowed IPs and persistent keepalive through separate non-secret `wg show` fields. Any mismatch or failed command refuses activation and leaves the existing creation intent and rollback machinery responsible for recovery. The verifier never invokes `wg show ... dump`, whose output can contain private-key material. The checks establish the configured peer values at observation time, not successful connectivity or protection against a separate privileged mutator racing later operations. The ownership-aware cleanup path refuses ambiguous kernel observations and passed the existing five-stage privileged lifecycle matrix. A separate disposable WireGuard acceptance probe now checks non-secret endpoint, allowed-IP and keepalive readback, followed by namespace absence after retirement. The targeted privileged probe passed. Neither probe establishes real-tunnel DNS confinement, IPv6 leak prevention or production provider connectivity.

## Named-profile resolution

`resolve_named_profiles` validates the complete version-one policy before returning an immutable ordered sequence of named entries with detached profile descriptions. An omitted selection resolves every profile in lexical name order; an explicit empty selection resolves none. Duplicate, unknown or malformed requested names are rejected. Each entry identifies whether it is the configured default.

This is an offline resolution contract only: it does not create resources, authorise privileged mutation or establish shared-tunnel ownership.

The disposable WireGuard peer-field and retirement probe passed privileged acceptance. the tested scope excludes production DNS confinement, application routing and independent privileged kernel mutators.

## Independent named-profile provisioning

The production restoration executor already processes eligible named profiles under its lifecycle lock and records a separate four-resource allocation batch, ownership bindings and durable creation intent for each profile. Multi-profile regression coverage now exercises two distinct pinned profiles, verifies that namespace and interface identities do not overlap, and confirms that a repeated restoration does not create further resources. A desired profile without a pinned provider plan is reported as not restored while another eligible profile can proceed.

These tests use an injected kernel harness and do not establish real concurrent VPN connectivity, shared-tunnel ownership, application routing or independent profile retirement. Those boundaries remain separate acceptance work.

## Selected-profile retirement

The ownership-aware cleanup executor accepts an explicit tuple of profile names to constrain retirement. An empty tuple makes no changes, while an omitted selection retains the established desired-policy cleanup behaviour. Unknown and duplicate names are refused. Resources belonging to unselected profiles remain outside the deletion plan, even if their ownership evidence would otherwise require review. Explicitly selected profiles can be retired even when present in the desired policy, but only after the existing ownership checks and dependency constraints pass. This does not establish application routing or shared tunnel ownership.

## Selected-profile lifecycle reconciliation

Adversarial cleanup tests verify that a selected prerequisite cannot be retired while an unselected dependent remains, while a selected dependent can be retired without deleting its prerequisite. A selected-profile deletion failure leaves unselected profiles untouched, and repeated successful retirement produces no further deletion. These tests use an injected kernel harness; the dedicated two-profile retirement probe has passed privileged acceptance, including preservation of the unselected profile and final teardown. The existing ownership and dependency checks remain the authority for deletion.

## Logical shared and isolated ownership

`resolve_ownership_groups` groups registered application consumers by their validated allocation keys. Applications using a shared profile contribute to one logical group, while applications using an isolated profile retain separate groups even when their VPN selection is identical. The groups and their consumer lists are immutable, deterministic and detached from the input policy. An unused profile does not create a consumer group. These keys are planning identities only: they are not kernel resource identifiers, persistent reference counts or proof that a tunnel can safely be reused or retired. The production lifecycle uses these keys to derive kernel allocation identities, but the keys alone remain insufficient to authorise privileged operations.

## Consumer reference release planning

`plan_consumer_release` evaluates an explicit set of registered application consumers against the validated policy. Releasing one consumer of a shared profile leaves the logical allocation retained while another registered consumer remains. Isolated application allocations are evaluated independently. Invalid or repeated consumer names are rejected, and results are immutable and deterministic. A result with no retained consumers means only that retirement can be considered; it does not provide a persistent reference count, verify a live tunnel or authorise resource deletion. The ownership-aware executor remains the sole destructive path; durable consumer evidence is checked separately from this read-only release plan.

Consumer-aware cleanup can optionally require a validated policy and an explicit release set alongside selected profiles. It refuses a selected profile when any registered consumer remains, and also refuses profiles without a released consumer group. This conservative check applies before any ownership-aware deletion is planned. It is not a durable live reference registry: callers must not treat policy-derived release decisions as proof that runtime consumers have actually stopped. The production cleanup executor continues to require independent creation-time ownership verification before deleting resources.

## Persisted consumer reference evidence

A private, versioned consumer-reference snapshot records a complete mapping of registered applications to their profile and logical allocation key, together with a declared active flag. The writer validates the entire snapshot, writes a restricted temporary file, synchronises it and replaces the target atomically. The reader rejects missing, symlinked, malformed, incomplete and policy-inconsistent evidence. When explicitly supplied to selected-profile cleanup, an active reference prevents retirement inside the existing lifecycle lock.

The snapshot is not a runtime reference registry. Its active flags are declared rather than independently attested, and an inactive flag cannot establish that a process has exited or that a tunnel is no longer in use. This evidence is an additional refusal condition, never deletion authority. Process-bound leases and independently verified kernel allocations provide separate operational evidence.

## Consumer reference transitions

Declared consumer references can be updated under a private advisory lock with an expected-state check. The transition refuses absent snapshots, unknown applications and stale state. This prevents competing cooperating writers from silently overwriting each other, but does not establish that an application started, stopped or released its tunnel. These declared transitions cannot authorise retirement; process-bound leases and kernel ownership verification are separate requirements.

## Consumer reference coordination during retirement

The cleanup executor holds the consumer-reference store's advisory lock throughout a guarded retirement operation, including kernel mutation. Cooperating reference transitions use the same lock, preventing a new declared acquisition from racing between the retirement check and deletion. Unsafe or replaced lock files are refused. This protects the consistency of declared reference evidence but does not establish process identity or kernel ownership. Runtime leases use the same reference-lock boundary, and isolated consumer retirement requires that evidence explicitly.

## Process-bound consumer evidence

The runtime consumer lease store records a registered executable, process ID, boot identity and process start time, together with the logical allocation key, exact generation ID and generation-specific kernel ownership profile. Acquisition checks the live Linux process identity and refuses mismatched executables or duplicate consumer leases. Release refuses a process that still has the original identity, and an expected-generation release refuses a lease belonging to another generation. Legacy version 1 leases remain readable but are not silently reinterpreted as generation leases. The store is policy-fingerprinted, serialised and atomically persisted. A failed or inaccessible process inspection does not silently discard a lease. A missing lease is not proof that a process is no longer using a tunnel.

`acquire_provisioned_consumer` is the ownership-verified acquisition path. It takes the established lifecycle lock before the consumer-reference lock, reads the durable journal, owner bindings and operation intents, and performs a fresh kernel ownership preflight. It refuses acquisition unless the consumer's kernel allocation has exactly one namespace and three interfaces, all with active lifecycle states and independently verified current owner bindings. The process identity is checked again before committing the lease. This operation binds a cooperating process to existing resources; it does not launch the application, change its network namespace or grant access to arbitrary resources.

## Shared and isolated production allocations

Production restoration expands isolated application consumers into distinct, deterministic kernel profile identities. These identities are derived from each application's logical allocation key and are recorded in the existing lifecycle journal, owner bindings and durable creation intents. Shared consumers retain the same kernel profile identity and resources. An unused isolated profile remains available for explicit named-profile management, but once it has registered consumers its template is not provisioned as an additional shared resource. Restoration refuses to reinterpret an existing live template allocation as consumer-owned resources; it requires explicit review and retirement instead.

Each isolated allocation can have its own pinned provider tunnel plan under its generated kernel profile identity. Credentials may be inherited from the original provider profile or pinned per allocation. Because overlapping host underlay networks would make routing ambiguous, restoration refuses overlapping host underlay plans before changing the kernel. Operators provisioning multiple isolated consumers must supply non-overlapping underlay addressing. The allocation mapping does not select providers or invent network addresses, and it cannot guarantee that an operator-supplied network is conflict-free with unrelated host routing.

Selected retirement resolves consumer references against the kernel allocation identities rather than treating every isolated consumer as a reference to one profile-wide resource. A retained lease vetoes retirement of its own allocation. Consumer-specific isolated retirement requires the durable runtime lease store and the validated policy; missing evidence is a refusal, not permission to delete. The existing identity-verified cleanup executor remains the sole destructive authority, with its lifecycle and reference locks held through deletion. Shared allocations remain protected by their registered consumer references and active leases.

An interrupted acquisition cannot silently replace an existing lease. A crashed consumer leaves its durable lease until its process identity can be shown to have exited or changed. An unreadable process is not silently released, and uncertain kernel ownership remains subject to the existing recovery and operator-review path. These are conservative cooperating-process guarantees, not an atomic transaction spanning process execution and the kernel. The isolated consumer retirement probe has passed privileged end-to-end acceptance. Its synthetic lease is now supplemented by the concurrent registered-launch acceptance described below. Resistance to independent privileged kernel mutators remains outside the evidence.

## Registered application packet confinement acceptance

`sudo python tools/probe_registered_application_confinement.py --run-privileged --uid UID --gid GID` composes the production-owned WireGuard fixture with one lease-gated VPN-bound child and one explicit direct child. Both children run as the selected non-root identity without supplementary groups. The VPN child holds the only runtime lease; the direct child remains in the host namespace and receives no lease.

Packet commands execute inside those registered children. While the tunnel is healthy, the VPN child completes IPv4 and IPv6 DNS exchanges and attempts UDP and TCP DNS traffic against reachable underlay listeners, which must receive nothing. The peer is then stopped without relaunching either child. VPN DNS remains unavailable, the underlay listeners still receive nothing, and the direct child continues to exchange IPv4 and IPv6 host-loopback datagrams. Restarting the peer restores DNS to the same VPN process. Child exit releases the lease before ownership-aware retirement, and the enclosing production fixture checks host routes, nftables and resolver contents against its baseline.

The probe also exercises a recovered profile containing retired generation history. Application namespace selection and lease reservation consider only active resources; multiple or incomplete active resource sets still refuse. This prevents a retired generation from making a valid current allocation appear ambiguous without permitting historical state to authorise a launch.

This is scoped guest evidence for the registered application path. It does not establish desktop resolver behaviour, encrypted DNS controls, host-VPN exclusion for direct applications or protection against independently privileged interference.

## Registered desktop session acceptance

`manage launch-consumer --desktop-session` replaces the minimal application environment with a validated graphical-session allowlist. The launcher still reconstructs `HOME`, `USER`, `LOGNAME` and a fixed `PATH` for the selected account. Locale variables and a small set of desktop identifiers may be forwarded. Loader, interpreter and arbitrary caller variables are excluded.

The target runtime directory must be exactly `/run/user/UID`, owned by that user and not writable by group or others. D-Bus is restricted to its `bus` socket. A Wayland display must be a relative socket name under the runtime directory and owned by the target user. X11 is restricted to a local display whose `/tmp/.X11-unix/XN` socket belongs to the user, together with an absolute user-owned regular `XAUTHORITY` file that is not group- or world-writable. Missing or non-standard session state refuses launch. In particular, the launcher does not search for a likely display or inherit the privileged caller's remaining environment.

The privileged `tools/probe_desktop_launch_acceptance.py` creates a nested session under the disposable guest's non-root account. Weston `15.0.1` supplies headless Wayland, Xvfb `21.1.25` supplies authenticated X11, and the systemd user runtime supplies D-Bus `1.16.2`. A registered direct child and a child released through the VPN privilege-dropping gate complete real protocol requests, read Xauthority and start descendants. Parent and descendant evidence must show the exact allowlisted environment, target UID/GID, empty supplementary groups and unchanged namespace identity.

This accepts the generic session boundary, not a complete desktop environment. Portals, notifications, audio, GPU rendering, tray integration, file pickers, compositor-specific activation and remote X11 are outside the evidence. Root-owned X11 sockets, absolute Wayland socket paths and non-standard D-Bus addresses are unsupported by the current contract. A caller using sudo must preserve the allowlisted session variables explicitly; their absence is a refusal, not a reason to infer values from unrelated processes.

## Consolidated application lifecycle acceptance

`sudo python tools/probe_application_lifecycle_acceptance.py --run-privileged --uid UID --gid GID` executes the disposable direct-routing and VPN-fallback refusal probe, the production registered VPN-bound launch gate across real A/B generations, the concurrent shared, isolated and direct lifecycle, registered direct and VPN-bound packet confinement, production provisioning integration, later interrupted-operation recovery and cooperating-process lifecycle-lock refusal. The runner refuses success if any stage fails or if the host's IPv4/IPv6 routes, nftables configuration or resolver contents differ after the matrix. Each child retains responsibility for its own disposable resources; the runner does not attempt unauthorised cleanup after failure. Without `--run-privileged` the command only previews its stages. The acceptance manager runs nested desktop-session integration separately inside the provisioned guest, so the lifecycle matrix does not require desktop packages on its caller's system.

The consolidated privileged application lifecycle matrix passed. Its registered launch stage invokes `manage launch-consumer --execute`, first proving refusal before production authority exists and then launching inspectable non-root children on the selected A and B namespaces. It compares each child with its durable allocation and generation lease and confirms lease removal after natural process exit. The concurrent lifecycle stage composes real shared, isolated and direct registered launches with lease-protected retirement and no-fallback refusal. The packet stage keeps registered VPN-bound and direct children alive together through dual-stack DNS, underlay bypass attempts, peer loss and recovery. The separate guest desktop stage exercises the validated session from direct and gated children and their descendants. These results must not be represented as universal DNS bypass prevention, compositor-specific desktop compatibility or protection against independently privileged kernel mutators.

### Live replacement readiness

`manage replacement-readiness --config PATH --profile NAME --runtime-consumers PATH` provides a read-only, lock-serialised check of a profile against current ownership evidence, desired-state convergence, pending operations and the policy-bound runtime lease store. Existing leases on A do not block independent preparation of B; they are reported as retirement blockers. Disputed ownership and unrelated non-convergence still block preparation. The report never authorises cut-over or retirement.

### Generation handover coordination

The `nordvpn_generation_handover` module records policy-pinned generation identities and their distinct kernel ownership profiles in private durable storage. `manage replace-profile --execute` provisions B through the production restoration executor, requires fresh creation-time ownership plus packet-level tunnel readiness, and only then activates B. `manage replacement-status` reconciles the durable record with fresh kernel ownership and leases. `manage retire-generation` removes only the requested old generation through ownership-verified cleanup and refuses live leases or reservations. Before retirement, the executor rechecks B's ownership and packet readiness under the lifecycle and consumer locks; a missing, disputed or unhealthy B prevents destructive cleanup. The packet-readiness observation checks the configured WireGuard peer and endpoint, transfer-counter syntax and DNS route interface against the pinned tunnel, alongside a DNS response and nonzero handshake. These observations do not establish permanent connectivity or immunity to subsequent drift.

Activation and application launch acquire lifecycle authority before consumer-reference authority. `manage launch-consumer` reads the configured profile handover, verifies and leases that same exact generation, places the suspended child in its verified namespace, and only then releases the pre-execution gate. Existing processes and their leases remain on A; no process is transparently migrated. Failure is closed: there is no automatic selection of A, another profile, the host namespace or `direct`. These locks coordinate cooperating Nord Tools processes; they do not claim protection against arbitrary privileged kernel actors.

## Generation handover recovery and drift assessment

`python nord_tools.py manage recover-generation --config /absolute/path/startup.json --profile PROFILE --runtime-consumers /absolute/path/leases.json` inspects the durable version 2 handover, the pinned policy, fresh ownership evidence and generation-specific consumer leases under the lifecycle and consumer locks. It reports whether the replacement is absent, partially present, independently verified, selected but unhealthy, draining, or ready for separately authorised retirement. For an active selection, the check also repeats the production packet-readiness probe and verifies the dedicated namespace nftables default-drop chains and exact allow rules, both default routes, the endpoint exception, and, where pinned, DNS destination routes, peer AllowedIPs and the exact namespace resolver file. This is not a passive network operation: packet verification sends a bounded DNS query through the namespace, without modifying routing configuration. The default command does not change the durable record or kernel state.

Adding `--execute` permits a prepared handover with a fully present, independently verified replacement to advance durably to `verified`. It does not activate the replacement, switch running applications, retire the old generation or silently roll back an active selection. Adding both `--execute --reprovision-absent` also permits the existing production replacement executor to reprovision a replacement that has no recorded resources and whose old generation remains independently verified. The production executor rechecks ownership and durable intent under its own locks before creating anything. A partial or disputed replacement, unresolved ownership, unexpected live resources, mismatched generation lease or active selected-generation drift is never treated as permission to create or delete resources. Those cases require operator review and the established ownership-aware recovery or cleanup procedure, with separate explicit authorisation.

This recovery interface is not a generic in-place kernel repair engine. It deliberately refuses speculative firewall, route, peer, DNS and resource deletion repairs where fresh creation-time ownership and exact desired state cannot establish a safe operation. Packet-level readiness establishes a bounded observation, not continuous tunnel availability. A separately privileged kernel mutator remains outside the cooperating-process authority guarantee. Production interruption and drift-injection acceptance is required before treating these recovery paths as operationally certified.

The disposable privileged generation-replacement probe now also checks read-only recovery classifications before B provisioning, after B verification, after activation while A retains a lease, and after A retirement. Its optional `--inject-replacement-interruption` mode terminates a worker with SIGKILL immediately after B has been provisioned, after durable activation, and after verified old-generation retirement, with the surviving parent re-observing and continuing through the established production paths. Run `sudo python tools/probe_live_tunnel_replacement.py --run-privileged --inject-replacement-interruption --uid UID --gid GID` on a suitable disposable-capable Linux host. The checkpoint coverage is deliberately specific: it does not prove every instruction boundary, every partial kernel mutation, or safety against independent privileged mutators. A failed probe retains its disposable evidence for operator review.

For a generation-managed application launch, the production pre-execution gate now also requires the pinned tunnel plan and checks the selected generation's dedicated nftables isolation rules, live default and endpoint routes, pinned DNS configuration and packet readiness while the lifecycle and consumer locks are held. These checks occur after the durable lease reservation but before the child is released to execute; a failure terminates the suspended child and retains the existing verified lease-release discipline. A read-only recovery report is not a persistent quarantine flag, so the launch gate must independently reject drift rather than trusting a previously healthy status result. The additional packet check can increase application launch latency, especially on slow or unavailable tunnels. Ordinary unversioned application launches retain their existing behaviour.
